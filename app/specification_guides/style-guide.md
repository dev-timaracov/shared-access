# Единый style guide: Python и DDD в FastAPI

Версия: 2. Общий стандарт для Python-кода любого проекта. Его основной текст
одинаков для всех проектов; структура конкретного проекта и согласованные
исключения описываются отдельно в `architecture.md` и решениях проекта.
Для проектов без Python этот документ не требует смены языка или стека.

## Размер и читаемость кода

- Файл Python — не более **500 SLOC**. Считать физические строки с исполняемым
  кодом, импортами и объявлениями; пустые строки, комментарии и docstrings не
  учитывать. Многострочное выражение занимает несколько SLOC. Разделять модули
  по предметной ответственности, не обходить лимит уплотнением кода.
- Функция или метод, включая async, — не более **50 физических строк** от первой
  строки `def`/`async def` до конца тела включительно. Многострочная сигнатура,
  docstring, комментарии, пустые строки и вложенные функции входят в этот лимит;
  декораторы перед определением — нет. Лямбды не использовать для обхода ограничения.
- Тело сценария по возможности состоит из вызовов небольших именованных функций:
  проверить вход, получить данные, применить правило, сохранить результат.
  Имена на английском отражают действие и предметное понятие, чтобы последовательность
  читалась как связный английский текст. Вынесение должно давать смысловое имя или
  отдельную ответственность; не создавать цепочки пустых делегирующих обёрток.
- Одна функция — одна операция на одном уровне абстракции. Отделять вычисления
  от I/O, использовать ранние выходы, избегать глубокой вложенности и скрытых эффектов.
- Комментарии оставлять только там, где причина или механизм действительно сложны:
  отмена и конкурентность asyncio, нетривиальные регулярные выражения, ограничения
  внешнего протокола. Сначала улучшить имена и структуру кода. Не комментировать
  очевидные действия и не хранить закомментированный код. Содержательные docstrings
  публичного контракта и необходимые директивы инструментов допустимы.

Лимиты проверять после форматирования, в том числе при ревью тестов. Сгенерированные
файлы и сторонний код выделять явно. Локальные исключения фиксировать с причиной
в архитектуре/решениях проекта; исторические превышения перечислять как технический
долг, не объявляя существующий проект соответствующим новому стандарту без проверки.

## Стиль Python

- Использовать поддерживаемую проектом версию Python из manifest/lock-файла.
  Обновление минимальной версии — отдельное согласованное изменение.
- Четыре пробела, UTF-8, `snake_case` для функций, модулей и переменных,
  `PascalCase` для классов, `UPPER_SNAKE_CASE` для констант. Имена отражают
  предметные понятия; избегать непонятных сокращений и общих `utils` для бизнес-логики.
- Аннотировать публичные функции, прикладные сценарии и порты; возвращаемое
  значение указывать явно. Использовать `Protocol` для структурных интерфейсов,
  `Enum` для закрытых наборов состояний, `dataclass` для предметных объектов,
  когда это уместно. `Any` оставлять на внешней границе и сужать после проверки.
- Не использовать изменяемые аргументы по умолчанию. Для коллекций полей
  применять `default_factory`. Не смешивать `None`, отсутствие значения и ноль.
- Docstring объясняет контракт, ограничения и побочные эффекты, а не пересказывает
  реализацию. Правила размеров, декомпозиции и комментариев описаны выше.
- Импорты группировать: стандартная библиотека, внешние пакеты, проект.
  Запретить wildcard imports и циклические зависимости. Локальный импорт
  использовать только с объяснимой причиной.
- Formatter — **Black**, с закреплённой версией в dev-зависимостях и CI. Базовая
  длина строки — 88; проект может явно закрепить другую длину в `pyproject.toml`.
  `black .` форматирует, `black --check .` проверяет. Ruff использовать для lint
  и порядка импортов с совместимыми настройками, не запускать конкурирующий formatter
  поверх Black. Типизацию проверять принятым mypy/pyright. Конкретные команды,
  версии и согласованные исключения закрепить в `testing.md` и CI. Переход
  существующего проекта с другого formatter оформлять отдельно от функциональных правок.
- Ловить конкретные исключения. Не подавлять ошибки через `except: pass`.
  Предметные ошибки имеют понятные типы; исходную причину сохранять через
  `raise ... from ...`, если её раскрытие безопасно.
- Логи структурировать по событию и идентификаторам операции. Секреты,
  содержимое токенов и приватные данные не логировать; настройки не хранить
  в коде. Время хранить с часовым поясом, обычно UTC; деньги — `Decimal`.

## Словари и JSON-подобные структуры

Словари, вложенные payload и dict-образные литералы оформлять как читаемый
отформатированный JSON-объект: открывающая и закрывающая скобки на отдельных
строках, одна пара ключ/значение на строку, отступ четыре пробела. Для строковых
ключей и значений использовать двойные кавычки. Оставлять завершающую запятую,
чтобы Black сохранял многострочный вид даже для короткого непустого словаря.

```python
payload = {
    "task_id": task_id,
    "options": {
        "dry_run": True,
        "timeout": None,
    },
}
```

Это правило оформления Python: сохранять `True`, `False`, `None` и допустимые типы
ключей; не подменять их JSON-литералами и не сериализовать данные в строку ради
форматирования. Пустой словарь — `{}`. Генераторы словарей и произвольные Mapping
оформлять по синтаксису Python; сложные преобразования выносить в именованные функции.

## DDD: язык, границы и модель

DDD (Domain-Driven Design) организует код вокруг предметных правил.
Сначала определить общий язык с владельцами продукта: одни и те же понятия
должны означать одно и то же в коде, API, тестах и документации.

- **Bounded context** — область со своей моделью и правилами, например каталог,
  управление доступом и задания загрузки. Между контекстами обмениваться
  явными контрактами/событиями, а не чужими ORM-объектами. Контекст не обязан
  быть отдельным сервисом; начинать можно с модулей одного приложения.
- **Entity** — объект с устойчивой идентичностью, меняющий состояние во времени.
  Например модель каталога или задание. Сравнение сущностей учитывает ID.
- **Value object** — значение без самостоятельной идентичности, например
  проверенный SHA ревизии, размер файла или путь объекта. Он валидируется
  при создании, обычно неизменяем и сравнивается по значению.
- **Aggregate** — граница согласованности с корневой сущностью. Изменения идут
  через методы корня, сохраняющие инварианты. Размер агрегата выбирается по
  требованиям согласованности, а не по всему графу таблиц.
- **Invariant** — правило, которое остаётся истинным после любой допустимой
  операции: нельзя публиковать неполный manifest или завершать отменённое
  задание. Проверять его в доменной модели, а не только в HTTP-валидации.
- **Domain service** — предметная операция, не принадлежащая естественно одной
  сущности. Не превращать его в универсальный класс всех сценариев.
- **Domain event** — факт уже состоявшегося изменения (`SnapshotPublished`).
  Событие отличается от команды (`PublishSnapshot`). Внешняя доставка события
  после commit требует outbox/повторов, если важна надёжность.

## Слои и направление зависимостей

```text
rest / cli / worker -> application -> domain
infrastructure -> application ports / domain contracts
composition root -> конкретные адаптеры и прикладные сценарии
```

| Слой | Ответственность |
| --- | --- |
| domain | Сущности, value objects, инварианты, предметные ошибки и события. Без FastAPI, HTTP, SQLAlchemy и сетевого I/O. |
| application | Прикладные сценарии, авторизация по проекту/ресурсу, координация портов, границы транзакций. Зависит от контрактов, не от конкретного SQL/S3/MQ клиента. |
| infrastructure | Реализации репозиториев, UOW, HTTP, S3, MQ и другие внешние адаптеры; преобразование ORM/провайдерских DTO в предметные объекты. |
| presentation | FastAPI routes, HTTP DTO, зависимости, преобразование ошибок в HTTP-ответы; вызов общего application-сценария. |
| composition root | Создание адаптеров и сценариев, внедрение зависимостей и управление ресурсами процесса. |

Порты объявлять у потребляющего их внутреннего слоя. Доменные объекты не
импортируют инфраструктуру. HTTP DTO/Pydantic-валидация описывают внешний
контракт, ORM — хранение; не делать один класс обязательной моделью всех слоёв.
Простой CRUD не требует искусственных агрегатов и десятков пустых классов.
Применять DDD там, где есть предметные правила; сохранять границы зависимостей.

Под прикладным внешним слоем здесь понимается **presentation**: REST/MCP/CLI,
обработчики сообщений и другие точки входа. **Application** — отдельный слой
координации сценариев; не смешивать их из-за похожих названий.

## Интерфейсы и внедрение зависимостей

- Межслойные зависимости направлять на порты (`Protocol` или `ABC`), а конкретные
  реализации подключать в composition root. Предпочитать интерфейсы при обращении
  к хранилищам, трекерам, HTTP, очередям, часам и другим заменяемым зависимостям.
- Интерфейс описывает операции, необходимые потребителю, а не все методы адаптера.
  Внедрять зависимости через конструктор или явные параметры; не создавать SQL/HTTP
  клиенты внутри бизнес-методов и не получать их из глобального service locator.
- Не оборачивать интерфейсом каждый value object и чистую функцию без причины.
  Интерфейсы защищают границы и позволяют подменять I/O в тестах; внутренний
  детерминированный код может вызываться непосредственно.

## DTO, сериализаторы и преобразование моделей

- Вместо прокидывания длинных списков полей от класса к классу передавать
  типизированные команды, запросы и DTO. Сигнатура показывает контракт сценария;
  единичный ID или скаляр не требует искусственного контейнера.
- Преобразования между внешним DTO, доменной моделью и моделью БД выполнять через
  явные сериализаторы/mapper-функции на соответствующей границе. HTTP-сериализатор
  принадлежит presentation, ORM/domain mapper — infrastructure. Домен не зависит
  от Pydantic, ORM или формата JSON. Не сериализовать модель в JSON и обратно
  для обычной передачи внутри процесса.
- Сопоставлять поля явно, проверять неизвестные и недопустимые значения, не передавать
  `**dto.model_dump()` в произвольный ORM/domain-конструктор без контроля полей.
  Входной DTO не может назначать серверную identity, scope, роль или другие защищённые поля.
- Не отдавать наружу живые ORM-объекты с lazy loading. Сохранять семантику ID,
  часовых поясов, Decimal, Enum, отсутствующего поля и `None` при преобразованиях.
  При изменении внешней схемы учитывать версионирование и совместимость.

## Декомпозиция application-сервисов

Один сервис/handler реализует один связный сценарий или небольшую группу сценариев
с общей ответственностью. Разделять сервисы по причинам изменения (SRP), а не
собирать управление всеми сущностями проекта в одном классе. Отдельные операции
создания, публикации, отмены и чтения могут иметь разные handlers и зависимости.

Application-сервис координирует доступ, загрузку через порты, вызов доменной модели
и сохранение через UOW. Предметные правила остаются в domain, SQL/HTTP — в адаптерах.
Не переносить доменную логику в application только ради лимита строк. Общие шаги
выделять в небольшие компоненты с ясным контрактом; не делать сервис, принимающий
все остальные сервисы, и не связывать handlers циклическими вызовами. Границу
транзакции определяет сценарий, декомпозиция не должна добавлять скрытые commits.

Repository, Unit of Work, агрегаты, value objects, фабрики и доменные события
применять по предметной необходимости. CQRS использовать, когда модели чтения и
записи действительно различаются; DDD не требует микросервисов или event sourcing.

## FastAPI, транзакции и async

- Route принимает/валидирует HTTP DTO, получает подтверждённую личность,
  вызывает сценарий и преобразует результат. Бизнес-правила не размещать в route.
  REST, MCP, CLI и worker используют тот же прикладной сценарий. Сервис проверяет
  доступ и scope, поэтому обход HTTP не даёт обхода авторизации.
- `Depends` использовать на границе FastAPI, а не в домене. Ресурсы процесса
  создавать/закрывать в lifespan, ресурсы запроса — через контекстные менеджеры
  и зависимости с `yield`; не подавлять их исключения.
  См. [FastAPI: dependencies with yield](https://fastapi.tiangolo.com/tutorial/dependencies/dependencies-with-yield/).
- Репозиторий предоставляет операции с агрегатами, не отдаёт наружу session
  или SQL-запрос. UOW управляет одной транзакцией сценария. Репозитории не делают
  скрытый `commit`; commit явный, при ошибке — rollback. Учитывать конкурентные
  изменения через ограничения БД/версионирование/блокировки по требованиям.
- Один `AsyncSession` на независимую asyncio-задачу; не делить session между
  параллельными задачами. Фоновая задача получает собственные ресурсы и ID,
  а не session запроса. См. [SQLAlchemy: concurrency model](https://docs.sqlalchemy.org/en/20/orm/session_basics.html#is-the-session-thread-safe-is-asyncsession-safe-to-share-in-concurrent-tasks).
- Не выполнять блокирующий I/O в event loop: использовать async-драйвер или
  явно выносить синхронную операцию в thread pool. Для клиентов задавать timeout,
  ограниченные retries и корректную обработку отмены. Не повторять необратимую
  операцию без стратегии идемпотентности.
- Не держать транзакцию/блокировку во время долгого скачивания. Подготовить
  внешние данные, затем коротко проверить состояние и атомарно опубликовать
  метаданные. БД и S3/MQ не образуют общую ACID-транзакцию: для согласования
  использовать outbox, идемпотентность, компенсацию и очистку незавершённой работы.
- Доменные ошибки преобразовывать в HTTP в presentation. Известные ошибки
  различать с неожиданными; не раскрывать traceback/секреты клиенту. Изменения
  модели хранения оформлять новой миграцией; исторические миграции не править.

## Пример MosaiHub

Референс: `https://git.mosai.pro/model-hub/backend.git`, проверенная ревизия
`4f2f1f790b0568996dac5879fe23e2bbf9775376`. В ней есть `src/rest`, `src/app`,
`src/domain`, `src/infra`, `src/app/factory.py`,
`src/infra/persistance/db/uow_factory.py`; модель и предметные типы находятся в
`src/domain/model/domain.py` и `src/domain/model/vo.py`.
Это пример организации кода, не утверждение полного соответствия стандарту.

Рекомендуемое применение к сценарию публикации модели:

1. HTTP handler передаёт команду `PublishSnapshot` прикладному сценарию.
2. Сценарий проверяет доступ к модели и использует порты хранилища/репозитория.
3. Value objects представляют ревизию и manifest; агрегат проверяет полноту,
   допустимость перехода состояния и соответствие подготовленных файлов.
4. Короткий UOW сохраняет manifest, итоговое состояние задания и outbox-событие.
5. После commit worker доставляет событие и выполняет повторяемую очистку
   неиспользуемых объектов. Сбой доставки не объявляется откатом уже сделанного commit.

Этот сценарий иллюстрирует границы ответственности; для конкретного проекта
агент обязан проверить реальный код и описать расхождения в `architecture.md`.

## Проверка изменений

Домен тестировать без сети/БД на инварианты и недопустимые переходы.
Сценарии — с fake-портами на авторизацию, транзакции и ошибки.
Адаптеры — интеграционно на реальной тестовой БД/сервисах, если это требуется.
HTTP — на контракт, валидацию, преобразование ошибок и передачу identity.
Добавлять проверки конкурентности, повторов и отмены там, где они влияют на результат.
Запускать проверки в порядке из `testing.md`; результаты фиксировать по единому
`report.md`, включая пропуски. В ревью проверять направление импортов,
инварианты, scope, транзакции и отсутствие секретов.
