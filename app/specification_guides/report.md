# Единая спецификация рабочего отчёта

Версия: 1. Применяется ко всем проектам Shared Access без изменения структуры.
Агент заполняет конкретный отчёт данными задачи; этот стандарт не переписывается
под проект. Отчёты создаются через `submit_work_report` и остаются неизменяемыми.

## Обязательные сведения

| Поле | Содержание и источник |
| --- | --- |
| Название задачи | Название из `get_task_context`: `tracker.snapshot.name`. |
| Дата | Дата и время регистрации отчёта из `report.created_at`, ISO 8601 с часовым поясом. До сохранения: «будет назначена сервером». |
| Статус | Статус задачи из `tracker.snapshot.state_id`; название, если трекер его предоставил. Указать свежесть и время получения. Отдельно указать результат работы `outcome`. |
| Список коммитов | `commits`: полные SHA всех относящихся к отчёту коммитов. Если коммитов нет: пустой список и явное указание незакоммиченных изменений. |
| Имя разработчика | Подтверждённое имя из профиля, если доступно; обязательный идентификатор — `report.developer_id`, назначенный сервером по авторизации. При отсутствии имени отображать идентификатор, не угадывать имя. |
| Имя агента | `agent_client` рабочей сессии, связанной с `report.session_id`, например Codex. Не выдавать имя агента за имя разработчика. |
| Краткое описание | Что сделано; в каком состоянии результат; что делать дальше. Использовать `summary`, `blockers`, `next_steps`, избегать неопределённых заявлений «всё готово». |
| Номер задачи в трекере | Человекочитаемый ключ/номер, если предоставлен (`identifier`), и внешний ID `tracker.item_id` / `external_id`. Номер без префикса проекта не считать глобально уникальным. |
| ID задачи в Shared Access | `task_id`, полученный при регистрации задачи; отличается от ID трекера. |
| ID отчёта в Shared Access | `report.id` из успешного ответа `submit_work_report` или истории. До сохранения: «будет назначен сервером». |

Статус задачи и `outcome` — разные сведения. `outcome` принимает `progress`
(промежуточная работа), `implemented` (реализовано, требуется предусмотренная
проверка), `blocked` (есть препятствие), `handoff` (передача работы).
Сохранение отчёта не переводит задачу в другой статус. Статус `done` нельзя
выводить из `implemented`. При недоступном трекере обозначать статус как
кэшированный/неизвестный и указывать `freshness` и `fetched_at`.

## Представление отчёта

```text
Название задачи: <название>
Дата: <report.created_at, ISO 8601 с часовым поясом>
Статус задачи: <название или state_id>; свежесть: <freshness>, получен: <fetched_at>
Результат работы: <outcome>
Коммиты: <полные SHA или «нет; изменения не закоммичены»>
Разработчик: <подтверждённое имя, если есть> (<report.developer_id>)
Агент: <session.agent_client>; сессия: <report.session_id>
Краткое описание:
  Сделано: <конкретные изменения и результат>
  Состояние: <проверено / не проверено / требуется ревью / блокеры>
  Дальше: <следующие действия или «нет»>
Задача в трекере: <ключ/номер, если есть>; внешний ID: <external_id>
Задача в Shared Access: <task_id>
Отчёт в Shared Access: <report.id>
Проверки: <команда, результат, tested commit SHA, доказательство; пропуски>
```

## Соответствие API и порядок работы

1. Зарегистрировать задачу, прочитать контекст и начать рабочую сессию. Сохранить
   внешний ID, локальный `task_id`, название, статус, свежесть и `agent_client`.
2. В `summary` включить название задачи, её внешний ID и статус со свежестью,
   затем кратко описать сделанное и текущее состояние. Заполнить `next_steps`
   и `blockers`. Это сохраняет сведения о задаче на момент отчёта, даже если
   название/статус трекера впоследствии изменятся.
3. Передать `task_id` как аргумент инструмента; в `report` передать `session_id`,
   `idempotency_key`, `outcome`, `summary`, `commits`, проверки и другие разрешённые
   поля. Название, статус и внешний ID фиксируются текстом в `summary`: отдельных
   входных полей для них сейчас нет. Не добавлять несуществующие поля в схему.
4. Получить `report.id`, `report.created_at` и `report.developer_id` из ответа.
   Для итогового представления объединить ответ, данные сессии и сохранённый
   контекст задачи. Серверные ID, дату и личность не передавать от имени агента.
   ID отчёта нельзя заранее включить в неизменяемый исходный payload.
5. Не изменять уже сохранённый отчёт. Исправление — новый отчёт с новым ключом
   и ссылкой на ID предыдущего. Идентичный повтор использует тот же ключ;
   изменённый payload обязан использовать новый ключ.

## Коммиты и доказательства

Использовать полные 40- или 64-символьные SHA. `head_sha` обозначает результат,
`checks[].commit_sha` — реально проверенный коммит. Для незакоммиченного дерева
указать `dirty_worktree=true`, описать состояние и не приписывать проверки
чистому коммиту. Указать PR/доступный артефакт передачи, если они существуют.
Для каждой проверки записать команду, `passed`/`failed`/`not_run` и доказательство
или CI URL. Пропущенные интеграционные проверки перечислять явно.
Git-ссылки и заявления агента не считаются проверенными CI/Git автоматически.
Не включать токены, пароли и другие секреты в отчёт.
