# Единый style guide: frontend

Версия: 1. Общий стандарт для JavaScript/TypeScript, компонентов, HTML и CSS.
Копируется при инициализации без изменений. Реальный стек, версии инструментов,
команды и исключения фиксировать в `architecture.md`, `testing.md` и решениях проекта.
Не вводить React, Vue, TypeScript или новый state manager только ради этого документа.
Для Python действует отдельный `style-guide.md`; Black к frontend не применяется.

## Размер, имена и читаемость

- Исходный файл — не более **500 SLOC**: физических строк с кодом, разметкой,
  объявлениями и стилями. Пустые строки и комментарии не учитывать. Для SFC считать
  script, template и style вместе; для JSX/TSX учитывать разметку. Сгенерированные
  файлы, lock-файлы и сторонние библиотеки явно исключать из оценки исходников.
- Функция, метод, callback или функциональный компонент — не более **50 физических
  строк** от начала определения до конца тела включительно. Считать сигнатуру,
  JSX, комментарии и пустые строки; для вложенных функций строки входят также
  в размер внешней. Проверять после форматирования, не уплотнять код ради лимита.
- Разбивать длинные страницы на компоненты с самостоятельной ответственностью,
  преобразования данных — на чистые функции, сценарии — на небольшие сервисы.
  По возможности тело сценария состоит из именованных шагов, читаемых как английский
  текст. Не создавать бессодержательные wrappers и абстракции для одной строки.
- `camelCase` для функций и переменных, `PascalCase` для типов и компонентов,
  `UPPER_SNAKE_CASE` для настоящих констант. Правила имён файлов согласовать
  с фреймворком. Использовать язык предметной области, избегать общих `data`/`manager`.
- Предпочитать ранние выходы глубокой вложенности. Не помещать сложную бизнес-логику
  в JSX, шаблоны, обработчики DOM и вычисляемые CSS-выражения.
- Комментарии использовать только для сложных причин и механизмов: гонки запросов,
  cleanup, особенности браузера, регулярные выражения, ограничения accessibility.
  Очевидное объяснять именами и структурой. Публичные TSDoc/JSDoc-контракты и нужные
  директивы инструментов допустимы; подавление проверки требует конкретной причины.

Исторические превышения и отличия инструментов перечислять как технический долг.
Не объявлять весь проект соответствующим стандарту без проверки и не переписывать
несвязанный код при реализации небольшой задачи.

## Форматирование и статические проверки

- Для нового проекта использовать **Prettier** и **ESLint**, с версиями в manifest
  и lock-файле. Один formatter; правила ESLint не должны спорить с Prettier.
  Базовые настройки: два пробела, `printWidth: 100`, завершающие запятые и единый
  стиль кавычек. Конфигурация проекта — источник фактических настроек.
- Команды форматирования и проверки закрепить в package scripts и `testing.md`.
  Не выдумывать отсутствующий `npm run lint`. Для существующего проекта миграцию
  инструментов выполнять отдельно, сохранять принятые версии и настройки.
- Использовать `const` по умолчанию, `let` при переприсваивании; не использовать `var`,
  неявные глобальные переменные, wildcard re-exports и циклические импорты.
- Объектные литералы и payload оформлять подобно отформатированному JSON:
  одна пара ключ/значение на строку, вложенность с отступами, завершающая запятая.
  Сохранять синтаксис JS/TS: методы, сокращённые свойства, `undefined` и типы;
  не преобразовывать объект в JSON-строку ради оформления. Пустой объект — `{}`.
  Formatter может сворачивать короткий объект: использовать поддерживаемую закреплённой
  версией настройку сохранения многострочной формы; не расставлять ignore повсеместно.

```typescript
const request = {
  projectId,
  options: {
    includeArchived: false,
    pageSize: 20,
  },
};
```

## Типы, DTO и преобразование данных

- Для нового TypeScript-кода включать strict-проверки. В JS-проекте использовать
  принятые JSDoc/проверки, не делать скрытую миграцию языка. Не заменять контракты `any`;
  внешние неизвестные данные принимать как `unknown` и сужать после проверки.
- Разделять HTTP DTO, предметную модель и view model. Формат API не должен определять
  внутреннюю структуру компонентов и store. Явные serializers/mappers на границе
  преобразуют даты, идентификаторы, nullable-поля, enum и ошибки.
- Передавать типизированные команды/объекты вместо длинных списков несвязанных
  параметров. Не копировать все поля DTO через spread в команды изменения или
  публичную view model без контроля разрешённых полей.
- TypeScript-тип не проверяет JSON во время исполнения. Проверять внешние данные
  на границе существующими средствами проекта; не подключать новую библиотеку
  схем ради одного преобразования. Различать отсутствие поля, `undefined`, `null`,
  пустую строку и ноль. Не сериализовать в JSON между обычными внутренними вызовами.
- Не мутировать входные props и общие объекты состояния. Явно задавать владельца
  изменяемого состояния; копировать только необходимую часть структуры.

## Архитектура, DDD и интерфейсы

```text
presentation (pages/components) -> application (use cases) -> domain
infrastructure (API/storage/browser adapters) -> внутренние порты
composition root -> конкретные адаптеры и сценарии
```

- **Domain**: предметные типы, value objects, правила и чистые преобразования.
  Без DOM, fetch, router, UI-фреймворка и browser storage.
- **Application**: сценарии, координация портов и клиентского состояния, обработка
  результатов. Один сервис/handler — одна связная ответственность (SRP);
  не собирать весь проект в один store или универсальный application-класс.
- **Infrastructure**: HTTP-клиент, storage, WebSocket, browser API и mapping DTO.
  Таймауты, транспортные ошибки и механика retries принадлежат адаптерам.
- **Presentation**: страницы, компоненты, hooks/composables и доступное взаимодействие.
  Отображает состояние и вызывает сценарий; не содержит URL API и предметные расчёты
  вперемешку с разметкой. Hooks/composables не должны становиться универсальным слоем
  для всей бизнес-логики.
- Заменяемые зависимости задавать через небольшие интерфейсы/контракты у потребителя,
  реализацию подключать в composition root. В JS достаточно явного объекта с нужными
  операциями. Не создавать interface для каждого компонента и каждой чистой функции.
- Организовывать функциональность по предметным областям; не импортировать внутренние
  детали соседней feature. Общие элементы выделять по реальному повторению, сохраняя
  предметные компоненты в своей области. Не создавать огромную папку `utils`.
- Использовать общий язык, bounded contexts и value objects там, где есть правила.
  Не копировать серверные агрегаты, репозитории и UOW в UI без необходимости.
  Клиентская проверка прав улучшает UX; окончательную авторизацию выполняет сервер.

## Компоненты, состояние и асинхронность

- Разделять серверное состояние, состояние URL и локальное состояние интерфейса.
  Не хранить вычисляемые значения вторым независимым источником истины. Для совместного
  состояния явно определить владельца; не поднимать всё в глобальный store.
- У каждой загрузки предусмотреть loading, empty, success и error; при обновлении
  отличать отсутствие данных от устаревших данных. Ошибки не маскировать пустым списком.
- Освобождать подписки, timers, observers и listeners. Отменять ненужный запрос через
  AbortController или средства проекта; защищаться от позднего ответа старого запроса,
  особенно при смене проекта, фильтров и unmount. Отмена не равна ошибке для пользователя.
- В React сохранять render чистым и не использовать effect для обычного вычисления
  производного значения; в других фреймворках соблюдать аналогичные lifecycle-границы.
  Использовать устойчивые ключи сущностей, не индекс изменяемого списка.
- Изменения с побочным эффектом защищать от случайных повторов. Optimistic update
  должен иметь rollback/revalidation и понятную обработку частичного сбоя.
  Не делать автоматические повторы неидемпотентной операции без договорённости с API.

## HTML, CSS, доступность и безопасность

- Использовать семантический HTML: button для действия, link для перехода, label
  для поля. Поддерживать клавиатуру, видимый фокус, порядок табуляции и возврат
  фокуса после закрытия диалога. ARIA дополняет семантику, не заменяет её.
- Показывать ошибки формы рядом с полями; не кодировать состояние только цветом.
  Давать изображениям подходящий alt, учитывать масштабирование, reduced motion
  и читаемость на узких экранах. Проверять доступность реальным взаимодействием.
- Применять существующие design tokens, переиспользуемые компоненты и локальную
  область CSS. Избегать глобальных селекторов, каскада `!important`, дублирования
  размеров/цветов и жёстких размеров, ломающих адаптивность.
- Экранировать внешний текст. Не вставлять непроверенный HTML через innerHTML
  или аналог фреймворка; rich text требует согласованной очистки. Валидировать
  назначения внешних ссылок и учитывать контекст вставки.
- Секреты нельзя включать в bundle и публичные frontend env-переменные. Сессию
  и токены хранить по модели безопасности проекта; не переносить их в localStorage
  для удобства. Не логировать токены и персональные данные.
- При SSR не разделять пользовательское состояние между запросами; не обращаться
  к window/document во время серверного render. Клиентские проверки не заменяют
  серверный контроль доступа, CSRF-защиту и ограничения API.

## Оптимизация frontend-кода

- Сначала определить проблему и baseline на production build с реалистичными
  данными, устройством и сетью. Dev mode и один быстрый desktop-запуск не доказывают
  качество UX. Измерять время сценария, LCP/INP/CLS, long tasks, память, объём JS/CSS
  и число запросов там, где это относится к задаче.
- Использовать browser Performance/Network/Memory и profiler фреймворка.
  Сравнивать до/после при одинаковых условиях, с повторениями; различать холодный
  и прогретый кэш. В отчёте фиксировать методику, результаты и ограничения.
- Сначала убрать лишние запросы, повторные обходы и O(n²) поиска по коллекциям.
  Индексировать по ID, порционно загружать большие данные. При необходимости
  виртуализировать длинные списки, сохраняя клавиатурную навигацию и доступность.
- Разделять bundle по маршрутам/крупным функциям, проверять стоимость зависимостей.
  Изображения отдавать подходящего размера, задавать размеры для предотвращения
  скачков layout; лениво загружать некритичный контент. Не откладывать главный
  видимый контент только ради общего правила lazy loading.
- Не делать тяжёлые вычисления и JSON-преобразования при каждом render.
  Мемоизацию, selectors и стабильные callbacks вводить после измерений: у них есть
  стоимость памяти и риск устаревших зависимостей. Не применять memo повсеместно.
- Группировать чтения и изменения DOM, избегать принудительных layout в циклах.
  Тяжёлые вычисления дробить или выносить в Web Worker, учитывая стоимость передачи
  данных. Не заменять измеренную проблему произвольным debounce на всех действиях.
- Для поиска выбирать debounce/throttle по UX-сценарию, отменять старые запросы,
  ограничивать параллелизм и объём результатов. Кэш ограничивать по размеру/времени,
  включать project/user/query в ключ там, где они меняют данные; очищать защищённые
  данные при смене пользователя. Кэш не заменяет проверку прав.
- Проверять утечки listeners, observers и удерживаемых больших объектов после
  повторных переходов. Оптимизация обязана сохранять точность, порядок, ошибки,
  доступность и модель безопасности. Усложнение без измеримого выигрыша отклонять.

## Тестирование и приёмка

Чистые domain/mapping-функции проверять unit-тестами без браузера и сети.
Компоненты — по поведению пользователя, loading/error/empty, клавиатуре и формам;
не привязывать тесты к внутренним полям и CSS-классам. Адаптеры — на HTTP-контракты,
отмену, ошибки и mapping. Интеграционные/E2E-сценарии — на критические переходы,
права и совместную работу подсистем. Моки не доказывают работу настоящего backend.

Запустить принятые formatter/lint/typecheck, тесты и production build из testing.md.
Для UI проверить целевые размеры экрана и браузеры; для SSR — hydration и изоляцию
состояния. В performance-тестах использовать контролируемую среду, не жёсткий тайминг
обычного unit-теста. Сообщить команды, результаты и пропуски по report.md.
Не объявлять команды доступными или проверки выполненными по одному этому документу.
