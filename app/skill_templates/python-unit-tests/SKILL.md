# Unit-тесты Python

Прочитай `AGENTS.md`, `docs/agents/testing.md`, `docs/agents/style-guide.md` и относящиеся к изменению разделы
`docs/agents/architecture.md` от корня текущего checkout. Проверь настройки тестового
раннера, зависимости, fixtures и соседние тесты. Используй существующий стек;
команды бери из проекта, не предполагай наличие pytest или конкретного менеджера пакетов.
Применяй style guide и к тестам: лимиты размеров, форматирование Black (или явное
исключение проекта), читаемые fixtures и словари. Если документа нет, обозначь пробел.

Определи наблюдаемый контракт по требованиям и вызывающему коду. Для исправления
ошибки добавь сценарий воспроизведения; по возможности проверь, что он падает до
исправления. Выбери значимые успешные, ошибочные и граничные случаи. Не закрепляй
текущее ошибочное поведение и не дублируй алгоритм реализации в ожидаемом результате.

Изолируй сеть, часы, случайность и внешнее хранилище на границах зависимостей.
Используй небольшие fixtures и штатные fake/mock; для async-зависимостей проверяй
ожидание вызовов. Тесты должны выполняться независимо, без реальных сервисов,
секретов, задержек и зависимости от порядка. Проверяй результат, ошибки и значимые
побочные эффекты; внутренние вызовы проверяй только когда они часть контракта.

Не выдавай тест с реальной БД, HTTP-сервером или несколькими подсистемами за unit-тест.
Если требование относится к SQL, блокировкам, миграциям или транспортному протоколу,
укажи необходимые интеграционные проверки отдельно: моки их не подтверждают.

Запусти сначала изменённые тесты, затем обязательные проверки из testing.md.
Сообщи команды, результаты и пропуски с причинами; не заявляй об исполнении по одному
наличию команды в CI. Не ослабляй assertions и не меняй контракт ради зелёного прогона.
