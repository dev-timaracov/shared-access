# Реализация по спецификации и архитектуре

Прочитай `AGENTS.md`, `docs/agents/architecture.md`, `docs/agents/testing.md`,
спецификацию задачи и применимый style guide от корня текущего checkout:
`docs/agents/style-guide.md` для Python, `docs/agents/frontend-style-guide.md` для
JS/TS, компонентов, HTML и CSS. В смешанной задаче используй оба документа.
Python guide определяет правила реализации: лимиты 500 SLOC на файл и 50 строк
на функцию/метод, Black, оформление словарей, декомпозицию, интерфейсы, serializers/mappers
и границы DDD. Применяй документированные исключения проекта; при отсутствии
документа сообщи об этом и используй существующие правила, не выдумывая стандарт.
Для frontend используй Feature-Sliced Design: слои, слайсы, сегменты, публичные API
и импорты вниз по слоям. Применяй его formatter, правила компонентов, состояния,
доступности и безопасности; backend-архитектуру и Python-инструменты на UI не переноси.
Для производительности следуй разделу оптимизации применимого guide: оцени объём
данных, сложность, запросы и границы параллелизма. Если задача об оптимизации,
сначала зафиксируй baseline, затем сравни результат на одинаковой нагрузке;
не заявляй ускорение без измерений и проверки неизменности контракта.
Сверь документацию с кодом, зависимостями, точками входа и тестами. Для удалённых
документов используй точную ревизию репозитория; при отсутствии документов обозначь
пробел, не подменяй их документацией main.

Если проект использует Shared Access, следуй его workflow: получи контекст задачи
и начни рабочую сессию до изменений, проверь свежесть и существующие отчёты. Если
нужный инструмент недоступен, сообщи об ограничении, не выдумывай ID и контекст.

Свяжи требования с критериями приёмки и существующими компонентами. Проследи поток
от публичного интерфейса к бизнес-логике, хранилищу и адаптерам. Размещай изменения
в слоях, определённых проектом; используй существующие интерфейсы и направление
зависимостей. Не вводи новый фреймворк или архитектурный слой без необходимости.
Общие правила доступа и бизнес-инварианты должны оставаться в общем сервисном слое,
если это предусмотрено архитектурой, а не дублироваться в транспортах.

При противоречии спецификации архитектуре сначала опиши конкретный конфликт.
Разрешай обычные детали реализации по правилам проекта; уточняй только решения,
которые меняют публичный контракт или не выводятся из требований. Продолжай независимую
работу, пока существенное уточнение ожидается. Не представляй предположение как требование.

Реализуй согласованный объём, сохраняя совместимость и правила авторизации. Изменения
схемы оформляй новой миграцией, если проект использует миграции; не редактируй историю.
Проверь критерии приёмки тестами подходящего уровня, включая ошибки и границы доступа.
Проверь изменённый код по style-guide.md и сообщи оставшиеся нарушения или исключения.
Запусти проверки из testing.md, устрани связанные сбои и обнови документацию изменённого
поведения. Не объявляй локальные моки доказательством работы реальной интеграции.

Сообщи результат, команды и результаты проверок, пропуски, риски и оставшиеся действия
по docs/agents/report.md, если он есть. Отчёт не переводит задачу в done; не выполняй
публикацию, развёртывание или переход статуса за пределами разрешённого объёма.
